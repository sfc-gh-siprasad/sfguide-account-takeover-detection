# Account Takeover Detection

A Snow Packs example: connect identity, session and transaction signals to flag explainable account takeover patterns, and give fraud investigators a ranked queue, a case timeline and a drafted case summary.

**Landing page:** https://sfc-gh-siprasad.github.io/sfguide-account-takeover-detection/ · **Try it in your browser:** https://sfc-gh-siprasad.github.io/sfguide-account-takeover-detection/try/

> **Illustrative example.** All data is synthetic. The rules are illustrative and are not production, fraud, security, or compliance advice. This is not an official Snowflake product and is not supported by Snowflake Support. Provided as is under Apache 2.0.

Owner: Siddharth Prasad · Last reviewed: November 2026

## What you get

A three-page Streamlit app:

| Page | What it shows | Snowflake capability (live mode) |
| --- | --- | --- |
| Alert queue | Customers ranked by triggered rules; tunable weights and threshold; rule filters | Rule views (`MATCH_RECOGNIZE`, `HAVERSINE`, window functions); weights in `RULE_WEIGHTS` |
| Case timeline | Rule evidence, logins, MFA, account changes and transfers in time order; case summary | Cortex `AI_COMPLETE` (top 20 alerts) |
| Rule performance | Precision and recall per rule and by alert threshold, against synthetic labels | Computed in the app |

The app runs in two modes from the same code:

- **Sample data (default):** no Snowflake account, no credentials. Case summaries are templated and labelled **Sample AI response**.
- **Snowflake:** the same app reads rule hits from the SQL rule views the setup scripts create, and shows case summaries generated by Cortex `AI_COMPLETE`.

### The rules

The detection window is 2 October to 1 November 2026; the month before is the customer's baseline.

| Rule | Fires when | Default points |
| --- | --- | --- |
| Takeover sequence | Password or phone change, then a new payee, then a transfer to that payee, within 24 hours of the change | 50 |
| Impossible travel | Two consecutive successful logins at least 500 km apart, faster than 900 km/h | 30 |
| New device + country | First-ever login from a device and a country, then a transaction in that session | 25 |
| MFA fatigue | An MFA approval after 5 or more denials in the previous 10 minutes | 35 |
| Credential stuffing | A successful login from an IP that failed against 8 or more customers | 20 |
| Unusual amount | A transfer of $1,000 or more, above 3 times the customer's baseline median | 15 |

A customer's alert score is the sum of the points for the rules that fired; customers scoring 40 or more are alerts. The same rules are in `app/detection.py` and `sql/03_detection_rules.sql`.

## Try it in your browser

https://sfc-gh-siprasad.github.io/sfguide-account-takeover-detection/try/ is a static, no-install version of the three screens on the same synthetic data, with no external dependencies. Scoring runs in the browser (`try/score.js`), so changing a weight re-ranks the queue. `try/build_data.py` regenerates `try/data.js` from the app's own code, and `try/test_score.js` checks that the browser scoring matches Python:

## Quick start (no Snowflake account)

Prerequisite: Python 3 with `pip`. About 5 minutes.

```bash
git clone https://github.com/sfc-gh-siprasad/sfguide-account-takeover-detection.git
cd sfguide-account-takeover-detection
python3 -m venv .venv && source .venv/bin/activate
pip install -r app/requirements.txt
streamlit run app/streamlit_app.py
```

Open the URL Streamlit prints.

## Run against Snowflake

### Prerequisites

- A Snowflake account with Cortex `AI_COMPLETE`, and access to the `llama3.3-70b` model, either in your region or through cross-region inference. Check with `SHOW CORTEX BASE MODELS`; to use a different model, edit `sql/04_case_summaries.sql`.
- A role that can create roles, warehouses and databases (for example `ACCOUNTADMIN`) for the one-time setup in `01_setup.sql`. Everything after that runs as a dedicated least-privilege role, `ATO_DEMO_ROLE`.
- A Snowflake connection configured for the Snowflake connector or CLI.

### Steps

1. Run the scripts in `sql/` in order:
   `01_setup.sql`, `02_data.sql`, `03_detection_rules.sql`, `04_case_summaries.sql`.
2. Install the live-mode package: `pip install "snowflake-connector-python[pandas]"`.
3. Start the app against your connection:

   ```bash
   SNOWFLAKE_CONNECTION_NAME=<your_connection> ATO_MODE=live streamlit run app/streamlit_app.py
   ```

   You can also switch **Data source** to **Snowflake** in the sidebar.
4. To run inside Snowflake, create a Streamlit in Snowflake app from the files in `app/` using the `ATO_DEMO_WH` warehouse and the `ATO_DEMO_ROLE` role.

To see the alerts in SQL: `SELECT * FROM ACCOUNT_TAKEOVER.DATA.ATO_ALERTS ORDER BY alert_rank;`

### What gets created

| Object | Name |
| --- | --- |
| Role | `ATO_DEMO_ROLE` |
| Warehouse | `ATO_DEMO_WH` (XSMALL, 60 second auto-suspend) |
| Database / schema | `ACCOUNT_TAKEOVER.DATA` |
| Tables | `CUSTOMERS`, `IDENTITY_EVENTS`, `ACCOUNT_CHANGES`, `TRANSACTIONS`, `RULE_WEIGHTS`, `CASE_SUMMARIES` |
| Views | `RULE_TAKEOVER_SEQUENCE`, `RULE_IMPOSSIBLE_TRAVEL`, `RULE_NEW_DEVICE_COUNTRY`, `RULE_MFA_FATIGUE`, `RULE_CREDENTIAL_STUFFING`, `RULE_UNUSUAL_AMOUNT`, `ATO_ALERTS` |

### Cost and time

Setup takes a few minutes; the data load is about 50,000 rows. Compute is one XSMALL warehouse that suspends after 60 seconds. The rule views only run when queried, and `AI_COMPLETE` runs once for 20 alerts. Expect a small amount of credits for an evaluation.

### Cleanup

Run `sql/99_cleanup.sql`. It drops the database (and everything in it), the warehouse and the role.

### Using real dates

The rule views fix the detection window at 2 October 2026 so Snowflake results match the sample data and screenshots. For real data, replace `'2026-10-02'::TIMESTAMP_NTZ` in `sql/03_detection_rules.sql` with a rolling window, such as `DATEADD('day', -30, CURRENT_DATE())`.

## The data

`data/generate_data.py` produces everything with a fixed seed, so numbers are identical on every run. It has 1,500 customers, about 33,500 identity events, 4,600 account changes and 12,800 transfers, over 1 September to 1 November 2026.

There are 40 confirmed takeovers:

| Attack style | Customers |
| --- | --- |
| Full chain from a new device abroad | 15 |
| MFA fatigue | 8 |
| Credential stuffing | 8 |
| Session hijack | 9 |

There are also 71 legitimate look-alikes: travellers, new phones with new payees, large purchases, VPN users and a few accidental MFA denials.

Names are invented. IP addresses come from private and documentation-only ranges. `CUSTOMERS.CONFIRMED_ATO` is synthetic ground truth, used only to measure the rules.

```bash
python3 data/generate_data.py   # rewrites data/*.csv and sql/02_data.sql
```

## Known limitations

- Tested in November 2026 on one AWS US East 2 account (model through cross-region inference) with Snowflake CLI 3.31, Streamlit 1.67 and Python 3.15: setup, data load, rule views, AI_COMPLETE, the app in both modes, and cleanup. The SQL views and the app flagged the same customers for every rule and produced the same alert ranking.
- The rules are views, not Dynamic Tables: Dynamic Tables do not support `MATCH_RECOGNIZE`. For a large event history, materialise the alerts on a schedule with a task.
- On this data, the default threshold of 40 catches 31 of the 40 takeovers with 62% precision. The session-hijack style alone scores 30, so it is missed unless you lower the threshold or raise the impossible-travel weight. Real rates depend on your data.
- In Snowflake mode the app reads each rule's hits and evidence from the six `RULE_*` views and applies the weights you set on screen. Sample mode runs the same rules in Python (`app/detection.py`). `ATO_ALERTS` uses the weights in `RULE_WEIGHTS`; with default weights it gives the same ranking as the app.
- Live case summaries exist for the top 20 alerts only. Others show the templated sample text.
